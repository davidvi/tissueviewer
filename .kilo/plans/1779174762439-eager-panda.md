# Fix: Overlay points don't follow horizontal/vertical flip

## Problem

Rotation works for overlay points because OpenSeadragon's `viewport.setRotation()` rotates the entire viewport, including HTML overlays added with `viewer.addOverlay(...)`.

Flipping (`viewport.setFlip()`) only mirrors the tiled image rendering — it does **not** transform the position of HTML overlays. So when the user toggles horizontal/vertical flip:
- The image flips correctly.
- The overlay points stay at their original (un-mirrored) viewport coordinates, so they no longer line up with the underlying features in the slide.

All affected logic lives in `client/src/views/slideView.vue`. There are two flavors of overlays, both affected:
1. **Manual numbered overlays** (right-click adders) — `overlaysLocal` + `addOverlay()` (lines 769–791), reloaded by `reloadOverlays()` (lines 708–713).
2. **CSV-loaded colored point overlays** — `currentPointOverlays` rendered by `updateVisiblePoints()` (lines 933–974) which calls `addColoredDotOverlay()` (lines 984–1020).

Relevant state and methods (component-local):
- `flipHorizontal`, `flipVertical`, `rotationAngle` (lines 396–398)
- `applyFlip()` (lines 741–758) — toggles OSD flip + fakes vertical flip as `setFlip(!h) + rotate 180°`
- `resetTransform()` (lines 759–767)
- `processCSV()` stores point locations as normalized viewport coordinates (lines 882–893), where `x ∈ [0, 1]` and `y ∈ [0, 1/aspectRatio]` (because OSD's viewport y-extent equals `imageHeight / imageWidth`).

## Approach

The cleanest and most reliable fix is to **transform the overlay coordinates at render time** based on the current flip state, and **re-render overlays whenever the flip state changes**. Coordinates are kept in their original (un-flipped) form in state; only the *displayed* `OpenSeadragon.Point` is mirrored.

### Coordinate transformation

Given viewport coordinates `(x, y)` with image bounds height `H = imageHeight / imageWidth`:

- Horizontal flip: `x' = 1 - x`
- Vertical flip: `y' = H - y`

`H` can be obtained safely at render time from:
```js
const bounds = this.viewer.world.getItemAt(0).getBounds();
const H = bounds.height; // == imageHeight/imageWidth in OSD's default coords
```

Note: `applyFlip()` already implements vertical flip as `setFlip(!h) + rotate +180°`. Because rotation already moves overlays correctly with the viewport, the *combined* transformation that overlays need to compensate for is exactly the same horizontal mirror that OSD applies to the image (`x → 1 - x` in viewport space, regardless of whether the user clicked H or V). The `+180°` rotation that simulates vertical flip is already applied to overlays automatically by OSD. So:

- If `flipHorizontal XOR flipVertical` is the OSD `setFlip` state actually in effect, mirror `x` accordingly.
- The vertical case's extra `180°` rotation is handled by OSD itself.

This means the only manual transformation we need is the horizontal mirror that matches the current `viewer.viewport.getFlip()` value. We can read it directly from OSD instead of recomputing from the two booleans:

```js
const flipped = this.viewer.viewport.getFlip();
const xView = flipped ? (1 - x) : x;
const yView = y;
```

This keeps the logic single-sourced and robust to the existing "vertical flip = h-flip + 180° rotation" trick.

## Changes (all in `client/src/views/slideView.vue`)

### 1. Add a helper that converts stored coords to display coords
Add a new method near the rotation/flip section:
```js
getFlippedPoint(x, y) {
  // Mirror x in viewport space when OSD's flip is active.
  // Vertical flip is handled by OSD's 180° rotation, which already moves overlays.
  const flipped = this.viewer && this.viewer.viewport.getFlip();
  return new OpenSeadragon.Point(flipped ? (1 - x) : x, y);
},
```

### 2. Use the helper inside both add-overlay paths
- `addOverlay(x, y, number, text)` (lines 778–782): replace `new OpenSeadragon.Point(x, y)` with `this.getFlippedPoint(x, y)`.
- `addColoredDotOverlay(x, y, color, ...)` (lines 1008–1012): same replacement.

### 3. Make `contextMenuHandler` store un-flipped coordinates
At lines 673–698, when the user right-clicks, the click position must be converted back to *original* (un-flipped) viewport coords before being stored in `overlaysLocal` / Vuex. Otherwise the stored coordinate will already be a "displayed" one and would double-flip on re-render.

After computing `elementCoordiantes`, undo the current flip so storage is canonical:
```js
const stored = this.viewer.viewport.getFlip()
  ? { x: 1 - elementCoordiantes.x, y: elementCoordiantes.y }
  : { x: elementCoordiantes.x, y: elementCoordiantes.y };
```
Use `stored.x`/`stored.y` everywhere this handler currently uses `elementCoordiantes.x`/`.y` (the push to `overlaysLocal` and the `addOverlay(...)` call). `addOverlay` will re-apply the flip via `getFlippedPoint`.

### 4. Re-render overlays via a single `flip` event handler
OSD raises a `flip` event on the viewer when `viewport.setFlip` is called (vendored OSD line 20670). Add a handler once inside `initializeViewer` near the existing `rotate` handler (lines 702–706):

```js
this.viewer.addHandler('flip', () => {
  this.reloadOverlays();
  if (typeof this.updateVisiblePoints === 'function') {
    this.updateVisiblePoints();
  }
});
```

Why this order:
- `reloadOverlays()` calls `this.viewer.clearOverlays()` (line 709), which wipes **all** overlays (arrows + dots), then re-adds arrows via `addOverlay` (now flip-aware).
- `updateVisiblePoints()` then re-adds the currently-visible CSV dots via `addColoredDotOverlay` (also flip-aware).

This is the single source of truth — `applyFlip()` and `resetTransform()` do **not** need explicit re-render calls because both already end up calling `viewer.viewport.setFlip(...)`, which fires the event.

Caveat: `applyFlip()` (lines 748–753) calls `setFlip` and `setRotation` for the vertical-flip path. If the new `setFlip` state equals the previous one, OSD's `setFlip` early-returns and does **not** fire the event (vendored OSD lines 20649–20651). In practice the user is toggling a checkbox, so the state always changes; but to be safe, also explicitly call the re-render at the end of `applyFlip()` and `resetTransform()` as a belt-and-suspenders measure, or refactor `applyFlip` to always change flip state. The simplest safeguard is to just add an explicit call at the end of `applyFlip` and `resetTransform`:

```js
// in applyFlip and resetTransform, after setFlip/setRotation:
this.reloadOverlays();
if (typeof this.updateVisiblePoints === 'function') {
  this.updateVisiblePoints();
}
```

Since the handler will also fire when flip actually changes, we should make sure we don't double-render. Two equivalent options:
- Keep only the handler; refactor `applyFlip` to set the new flip state exactly once. (Cleaner.)
- Keep only the explicit calls at the end of `applyFlip`/`resetTransform` and *not* add the global handler. (Simpler diff.)

Going with the user's chosen approach: **use the OSD `flip` event handler as the single source of truth**, and refactor `applyFlip()` slightly so it makes exactly one `setFlip` call (avoiding the duplicate call on lines 744 and 752 / 755 in the current code). This ensures the handler fires exactly once per user toggle.

Refactored `applyFlip()`:
```js
applyFlip() {
  if (!this.viewer) return;
  if (this.flipVertical) {
    // Vertical flip = horizontal flip + 180° rotation
    const effectiveRotation = (this.rotationAngle + 180) % 360;
    this.viewer.viewport.setFlip(!this.flipHorizontal);
    this.viewer.viewport.setRotation(effectiveRotation);
  } else {
    this.viewer.viewport.setFlip(this.flipHorizontal);
    this.viewer.viewport.setRotation(this.rotationAngle);
  }
},
```

### 5. Reset path
`resetTransform()` (lines 759–767) already calls `setFlip(false)`, which will fire the same `flip` event and trigger re-render automatically. No changes needed beyond what's already there — overlays will return to their canonical positions because `getFlippedPoint` will see `getFlip() === false`.

## Out of scope / not changed

- OSD's internal HTML-overlay layer is not modified.
- The store schema (`overlays`) is unchanged.
- The "vertical flip = h-flip + 180° rotation" trick in `applyFlip()` stays as-is — it works for the image, and with this fix, also for overlays (since the 180° part already moves overlays correctly via rotation, and the h-flip part is compensated by `getFlippedPoint`).

## Validation

Manual test matrix in the running app:
1. Load a slide, add a couple of right-click arrow overlays, load a CSV of points.
2. Toggle `flipHorizontal` — image and all overlay points should mirror together.
3. Toggle `flipVertical` — image and overlays should mirror vertically together.
4. Toggle both — both transformations compose correctly.
5. Rotate while flipped — rotation continues to work and overlays remain pinned.
6. Add a new arrow overlay while flipped — it should appear under the cursor and remain pinned when flip is toggled off.
7. Reset transform — overlays return to original positions.
8. Pan/zoom while flipped — `updateVisiblePoints` keeps culling correctly (its bounds check works in viewport space, which `setFlip` does not change, so this should "just work"; verify regardless).

# Follow-up: Rotation direction reversed when flipped

## Problem

After the overlay-flip fix shipped, the user reports: while the image is flipped, the rotation control rotates the *visible* image in the wrong direction. A "rotate clockwise" input rotates the (flipped) image visually counter-clockwise.

## Why

This is a general property of mirror transforms: reflecting then rotating by `+θ` is visually equivalent to rotating by `-θ` then reflecting. With OSD, the render pipeline applies rotation first, then flip. So whenever OSD's effective horizontal flip is on, the rotation appears reversed on screen relative to the angle we pass to `setRotation`.

OSD's effective horizontal flip is currently:
- `flipVertical=false`: `flipHorizontal`
- `flipVertical=true`:  `!flipHorizontal`

i.e. `osdFlip = flipHorizontal XOR flipVertical`.

So when `osdFlip` is true, we need to negate the rotation angle before handing it to OSD, so that the *visible* image rotates in the direction the user intended.

## Approach

Whenever we push rotation+flip state to OSD, sign-correct the rotation:
```
osdAngle = osdFlip ? -userAngle : userAngle
```

Note: the existing `+180°` trick used to simulate vertical flip is unaffected — `-180° ≡ 180° (mod 360)`, so adding 180° before or after negation is the same.

## Changes (all in `client/src/views/slideView.vue`)

### 1. Centralize the transform push
Replace the three places that call `viewer.viewport.setRotation` (in `applyRotation`, `rotateBy`, `applyFlip`) with a single helper that always re-pushes both flip and rotation together. This guarantees the sign correction is applied consistently.

New helper (near the other rotation/flip methods):
```js
_pushTransform() {
  if (!this.viewer) return;
  const baseAngle = this.flipVertical ? (this.rotationAngle + 180) : this.rotationAngle;
  const osdFlip   = this.flipVertical ? !this.flipHorizontal : this.flipHorizontal;
  const osdAngle  = osdFlip ? -baseAngle : baseAngle;
  const normalized = ((osdAngle % 360) + 360) % 360;
  // Set rotation first (with suppression) then flip — order doesn't matter
  // mathematically but we want the 'flip' event to be the last thing that
  // fires so the overlay re-render sees the final rotation state.
  this._suppressRotateSync = true;
  this.viewer.viewport.setRotation(normalized);
  this._suppressRotateSync = false;
  this.viewer.viewport.setFlip(osdFlip);
},
```

Then:
- `applyRotation()` becomes: `this._pushTransform();`
- `rotateBy(degrees)` keeps its angle update and then calls `this._pushTransform()` instead of `setRotation` directly.
- `applyFlip()` becomes: `this._pushTransform();` (drops the inline if/else — same logic moved into the helper).

### 2. Guard the `rotate` event handler
Because `_pushTransform` passes a sign-flipped angle to OSD, the existing `rotate` handler (lines 709–712) — which reads `viewport.getRotation()` back into `this.rotationAngle` — would corrupt `rotationAngle` after every programmatic update (it would store the OSD-side angle, not the user-side angle).

Add a one-shot suppress flag and respect it in the handler:
```js
this.viewer.addHandler('rotate', () => {
  if (this._suppressRotateSync) return;
  // Only fires when something *outside* our methods changed the rotation
  // (e.g. OSD's built-in keyboard shortcut). Best-effort sync — invert the
  // sign correction so the slider stays consistent.
  const osdRot = this.viewer.viewport.getRotation();
  const osdFlip = this.viewer.viewport.getFlip();
  let unsigned = osdFlip ? ((-osdRot % 360) + 360) % 360 : osdRot;
  if (this.flipVertical) unsigned = ((unsigned - 180) % 360 + 360) % 360;
  this.rotationAngle = parseFloat(unsigned.toFixed(1));
});
```

OSD fires the `rotate` event synchronously inside `setRotation` (see vendored OSD line 17696), so the flag pattern is safe.

### 3. Reset path
`resetTransform()` sets `rotationAngle = 0, flipHorizontal = false, flipVertical = false` and then directly calls `setRotation(0)` + `setFlip(false)`. Replace those direct calls with `this._pushTransform()` so the same code path is exercised:
```js
resetTransform() {
  this.rotationAngle = 0;
  this.flipHorizontal = false;
  this.flipVertical = false;
  this._pushTransform();
},
```
At this point `_pushTransform` will compute `osdFlip=false`, `osdAngle=0` — equivalent to before, but routed through the single helper.

### 4. `flip` event handler — unchanged
Still re-renders overlays on `flip`. Because `_pushTransform` always calls `setFlip` last, and overlay positions depend on the latest rotation (already applied via `setRotation`), the re-render sees the correct final state.

## Edge cases considered

- **Rotation slider input:** When the user types/drags `rotationAngle`, `applyRotation` runs → `_pushTransform` flips sign when needed → OSD sees `-angle` → visible image rotates the right way. The user's `this.rotationAngle` stays as the intended value.
- **`rotateBy(+90)` while flipped:** `rotationAngle += 90` (user-space), then `_pushTransform` negates if flipped → visible rotation is `+90°` clockwise as intended.
- **Toggling flip with a non-zero rotation:** `applyFlip` is called, which routes through `_pushTransform` — the rotation immediately re-signs based on the new flip state, so the visible orientation stays consistent across the toggle. (The user's stored `rotationAngle` does not change.)
- **OSD built-in rotate (if ever triggered):** The handler's inverse sign-correction keeps the slider state roughly in sync, though composing it with vertical-flip's `+180°` offset is best-effort.

## Out of scope

- Negating zoom or pan — unaffected by this issue.
- Changing the user-facing rotation slider's range or sign convention — `this.rotationAngle` still represents the visible-clockwise angle the user dialed in.

## Validation

1. With flip off: rotate left/right buttons and slider behave as before.
2. With `flipHorizontal=true`, `rotationAngle=0`, rotate +30° via slider → visible image rotates 30° clockwise (not counter-clockwise).
3. Same with `flipVertical=true` only.
4. With both flips on: rotation direction returns to "normal" (double mirror = no mirror).
5. Toggle flip on/off while rotated: visible orientation matches user expectation, slider value doesn't jump.
6. Reset transform: clears to 0/0/0 cleanly.
7. Overlay points still follow flip + rotation correctly (the previous fix continues to work because overlays move with `setRotation` automatically; our negation only changes the value passed to OSD).
